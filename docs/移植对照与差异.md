## 3.2 大响应尾部截断修复（2026-11-11）

**症状**：>256 KiB 的响应在最后几个字节被截掉，`curl` 报 `PARTIAL_FILE`（rc=18）。实测
`512 KiB` 静态文件得到 `524282` 字节（少 6 B），sha256 不匹配；GitHub / Cloudflare 首页
`TUNNEL_FAIL`。小响应（OPEN_OK、几百字节页面）完全正常，所以早期自检的 64 KiB 用例抓不到。

**根因**（两处叠加，都在 `src/app/tunnel.ts`）：

1. `Stream.write()` 只接受发送窗口内的字节并返回接受量（`stream.ts:107-116`）。服务端
   `target->tunnel` 分支在 `n < chunk.length` 时只 `sock.pause()`，**余量直接丢弃**；
   客户端有 `pendingLocal` 队列，服务端没有对应的反向队列。
2. `sock.on('end')` 立刻 `closeWrite()` 发 FIN，不等余量写完，于是对端在缺字节的位置收到 EOF。

**修改**：

| 位置 | 改动 |
|---|---|
| `ServerTunnel` | 新增 `pendingToTunnel` 队列、`endFromTarget`、`paused`、`pumping` |
| `TunnelServer.pumpToTunnel()` | 按 `write()` 返回值保留余量；队列非空则 pause 目标 socket，排空后 resume |
| `TunnelServer.tick()` | 每 10 ms 排空 backlog（窗口被 ACK 打开时继续推进） |
| `sock.on('end')` | 只置 `endFromTarget`，FIN 在 backlog 排空后才发 |
| 客户端 `flushPending()` / `sock.on('end')` | 同一规则：FIN 不越过本地待发余量 |
| `cleanup()` | 会话关闭时清空两个方向的队列 |

**反证与回归**：

- 修复前（VPS 旧代码）512 KiB → 524282 B，hash 不符；修复后 → 524288 B，hash 与 VPS 侧一致。
- `scripts/self-interop.mjs` 的载荷从 64 KiB 提到 **320 KiB**（> 256 KiB 窗口），
  修复前该用例会缺字节、修复后逐字节通过；`tests/self-interop.test.ts` 同步改名。

**另一处部署陷阱（非代码）**：`-m` 既是本端发送预算也是接收端 `maxSymbolLen` 上限。一端
`1040`、另一端用默认 `1400` 时，1400 端所有 1.3 KB 级 symbol 会被 1040 端整包丢弃，
表现为「握手成功、OPEN_OK 正常、稍大的响应全部超时」。服务端 `ExecStart` 必须与客户端一致。`

## 3.3 `--trace` / `replay` 子系统修复（2026-11-11，十轮对抗分析）

**背景**：`--trace=PREFIX` 只写「每会话控制器 JSONL」，`replay` 只做汇总。对抗分析发现

| 7 | SIGINT/SIGTERM：`tunnel.stop(); process.exit(0)` 丢掉所有还在缓冲的尾部 | 500 行写入 + 立刻 `exit(0)` → 文件 **0 行**；加 200 ms 宽限 → 500 行 | `flushTraces()` 等每个文件 `close`（2 s 上限），`shutdown` 里先 await 再退出 |
| 8 | 无背压：`stream.write()` 返回值被忽略，慢盘下缓冲无上界 | 20 MB 传输实测 601 行 / 31 KB，本身不大，但写路径无上限 | 超过 `TRACE_MAX_BUFFERED`（1 MiB）丢弃新行并计数，`close()` 时汇报丢弃条数 |
| 9 | 坏行/半行被静默跳过，`{"t":5}` 会被当成事件类型 `5` | `replay` 只打印 `kinds`，看不出丢了多少 | `summariseTrace()` 返回 `malformed` 计数（坏 JSON、读取失败），非字符串 `t` 归入 `unknown` |

**结构变化**：写入器与读取器合并进 `src/util/trace.ts`（原先写入端在 `tunnel.ts` 的
`traceWriter`、读取端在 `cli.ts` 的 `replay()`），两侧共用同一套命名规则，避免再次漂移。
`tunnel.ts` 改为 `sessionTrace(opts, role, key)`。

**反证**：

- 缺陷 1：修复后同一命令 → 目录自动创建、`small=1048576` 完成、日志无 `ENOENT`。
- 缺陷 2/3/4：`--trace=<dir>` → 明确报错 + 建议前缀；`--trace=<绝对前缀>` → 文件数正确；
  目录里同时放 `cache.jsonl` / `cfg.jsonl` / `c-client-aa.jsonl` 时只计 1 个文件。
- 缺陷 7：SIGTERM 后文件末字节为 `\n`，全部行 `JSON.parse` 通过。
- 新增 `tests/trace.test.ts` 15 例，门禁 `51 passed / 0 failed`（原 36）。

**仍在的已知限制**：trace 文件不按大小/日期滚动（长时间跑会一直追加）；文件名用会话 salt
区分，没有 run id，跨多次启动的轨迹在 `replay` 里会合并统计。

## 3.4 吞吐优化（2026-11-11，真实 VPS 链路）

起点：本机 → VPS `144.34.186.164:4461` 经 SOCKS5 下载
`downloads.claude.ai/.../claude.exe`（344 807 072 B）实测 **107 KB/s**，
按此速率需约 54 分钟。

**2026-11-12 07:30 复测（同一路径、同一配置、代码只多了一条日志批处理修复 #12）**：
完整下载 **344 807 072 B / 144.77 s = 2.38 MB/s**，20 s 采样三次
2 146 360 / 2 181 684 / 2 196 194 B/s；该文件现在约 2.5 分钟下完。

> 2026-11-11 当晚的收尾数字是 1.08 MB/s（1 077 043 / 1 118 234 / 1 052 264 B/s）。
> 同一个 `--log-level=info` 配置、同样的代码路径，隔夜复测就变成 2.2–2.4 MB/s，
> 这段差距**不是代码造成的**（当晚到今晨之间只改了日志实现，而 info 级别总共只打
> 十几行），只能归因于跨境路径的时段性差异。记录在此以免把路径波动误读成优化成果。

### 对照实验（先定位，再改）

| 实验 | 结果 | 结论 |
|---|---|---|
| 进程内 `speedtest` | 2.4 MB/s | 协议栈本身不是瓶颈 |
| 本机 SOCKS 跑 5 MiB 本地文件 | 6.45 MB/s（修 UDP 缓冲前 185 KB/s） | 环回无丢包时很快 |
| VPS 直连下载同一文件 | 115 MB/s | 源站与 VPS 出口不是瓶颈 |

关键结论：**丢包只发生在下行，且是路径固有（16.5%）**，不是协议开销造成的；

## 3.5 三处结构性修复（2026-11-12，按用户指定的三项）

### 前提：这一轮的宏观速率不可比

同一条链路在 3 小时内塌了 9 倍，所以任何跨时段的吞吐对比都无效：

| 时间 | 测量 | 结果 |
|---|---|---|
| 07:39 | FCP 完整下载 329 MB | 2.38 MB/s |
| 09:30 | 裸 UDP 容量（sink） | 0.53 MB/s |
| 10:30 | 裸 UDP 容量（sink） | 0.27 MB/s |

因此本节的结论全部建立在**协议内统计量**上（重传构成、窗口占用、丢失率、重排占用），
以及**本机环回 0% 丢包**的对照上——这两者不受路径时段影响。

### 修复 A：发送窗口的估计源换成本方向的已确认字节

`updateStreamWindows` 原来用 `bbr`（由 `stream.read` 喂，即**接收**方向）推算**发送**窗口。
下载时接收方向只有 ACK 涓流，估出来的「带宽」0.1–0.5 MB/s，而实际下行 2 MB/s，
所以窗口从来不会按 BDP 放大，一直靠 512 KiB 下限兜着。

现在两半各用各的方向：

- 发送窗口 = 2 × (cum-acked 字节速率 × srtt)，下限 128 KiB；
- 接收窗口（advertise 给对端的 rwnd）= 4 × (read 字节速率 × srtt)，下限 1 MiB。

`StreamCallbacks` 新增 `acked(bytes, nowMs)`，由 `onAck` 里 cum 前移时回调；
`Session` 里两个 `BbrLite` 实例分别喂发送/接收方向。

**一个自己引入又修掉的回归**：第一版把**两半都**用发送方向估算。结果下载时上行空闲，
客户端 rcvBuf 永远停在 256 KiB，`rwnd=241058`，下行被死锁在 256 KiB / 0.46 s ≈ 0.5 MB/s。
这正是「一个估计喂两个方向」的反向版本，两半必须分开。

**接收缓冲为什么用 4× 和 1 MiB 下限**：它不是速率旋钮，是存活缓冲。实测 `reorder`
占用到达 257 KB 时缓冲（256 KiB）已满，此后接收端开始丢弃**已经收到过**的段，
发送端只能重传，重传副本又被丢——重传率 40% 的直接来源。调大后同一时段 `reorder`
仍在 257 KB，但不再顶到上限，丢弃消失。

### 修复 B：重传只发「被 SACK 证明丢失」的段，且不能早于一个 RTT

实测构成（服务端 `retxSplit`）：`1355/6/471`——快重传 1355 份、RTO 仅 6 份，
说明浪费全部来自快重传路径。根因两条：

1. **判据**：只要收到 3 个重复 ACK 就重传 `tx` 里最老的 6 个未 SACK 段。
   但重复 ACK 也可能是我们自己重传副本的回声——接收端早就有了，只是 cum 不动。
   于是「重传 → 回声 → 再重传」，两个连续采样窗口出现 **发送 162 段、其中 162 段全是重传**，
   同时 300 KB 新数据堵在队列里，因为窗口被副本占满。
   现在只有 `sackedHigh`（对端报告收到过的最大偏移）越过的段才算「证明丢失」，
   单凭 cum 的重复 ACK 不再触发重传。
2. **时序**：冷却固定 120 ms，短于 200–400 ms 的路径 RTT，副本还在飞就被再发一次。
   现改为首次重传至少等 `min(1.25×minRtt, srtt)`，重复重传再等 1.25 倍。

顺带把空洞期的紧急 ACK 从「每段一个」改成「每两段一个」：原来 800 段/s 就是 800 个
ACK/s，每个都立刻单独成包发出。

**证据（本机环回，0% 丢包）**：32 MiB 下载 `retx=12/21239` = **0.06%**，
其中 `retxSplit=0/12/0`——快重传 **0 次**、0 次触发；速率 13.1 MB/s，sha256 精确匹配。
说明这套判据在没有丢包时完全不产生多余重传，VPS 上 30% 的比例是路径真有 30% 丢包。

### 修复 C：FEC 控制器改用「未被首手收到」的比例，分母是发出的段数

原信号 `1 - setsPartial/groups` 在 16.5% 丢包下落在 0.80–0.99 灰区，k 整个会话不动。
换成丢失率之后还有第二个陷阱：分母如果用 `dataDelivered`（已交付段数），
**FEC 修不好的组根本不在分母里**，于是修得越差、链路看起来越健康——
实测在 28–35% 丢包时报出 **4.2%**，把 k 一路压到 1，形成自我实现的低估。

最终信号：`1 - ΔdataRxOrig / (Δ(setsFull+setsPartial) × d)`，用两次 FECSTAT 的**增量**
而不是会话累计值，目标 `k = ceil(d × loss × 1.5)`，没有灰区。有丢包立即升，
降到目标值需要连续 4 个低丢失样本（8 s）才降一步。

实测同一时段：P=3 时 `loss=35.0% k=3`（顶在协商上限），P=6 时 `loss=48.9% k=6`、
`loss=24.5% k=4`——控制器第一次真的在动。

### 配置改动：VPS 与客户端的 parity 上限 3 → 6

这不是第四项修复，是让 C 有意义的必要前提：P=3 时 k 顶在天花板，
控制器只能报告「我需要更多奇偶校验」而无能为力。改法只有两个参数：

- `fcp-node.service`：`--fec=10:3` → `--fec=10:6`
- `scripts/start-client.cmd`：同上（两端取 min，必须一起改）

代价为零的理由：k 由丢失率决定，干净链路上 k 会降到 1，与上限无关。
环回验证 P=6 无丢包时 33 MiB/2.79 s = 12.0 MB/s、哈希精确，与 P=3 的 13.1 MB/s 同量级
（差异在本轮单采样噪声内）。若某条链路更在意带宽而非恢复能力，把这两个参数改回 `10:3` 即可。

### 仍未验证

1. **修复后的稳定吞吐**：链路 3 小时内从 2.38 掉到 0.27 MB/s，无法给出可比数字。
   需要在链路恢复后重跑 `sh scripts/ab-one.sh NEW 3`，与当时的裸 UDP 容量同屏对比。
2. **`firstAfter ≈ 1 RTT` 的代价**：丢包恢复比经典快重传晚约半个 RTT，
   在 2×BDP 窗口下理论上不影响管道占用，但没有实测验证。
3. **P=6 下的 `k` 收敛速度**：4 个样本（8 s）才降一步，短连接基本停在初始 k=3。


## 3.6 现场复测暴露的两处缺陷（2026-11-12 下午）

§3.5 的三项修复部署后没有做过端到端验证。这一节先复测现状，再修掉复测暴露的两个问题。

### 复测：功能正常，但两个数字在说谎

| 检查 | 结果 |
|---|---|
| `fcp-node` 服务 | active，10:50 启动，UDP 4461 |
| 本地/VPS 源码哈希 | 四个关键文件完全一致 |
| 出口 IP（经 socks5h 访问 api.ipify.org） | `144.34.186.164`，流量确实从 VPS 出 |
| example.com | HTTP 200 |
| 三次大文件下载 | 2.26 / 1.93 / 1.14 MB/s，均完整 |
| 服务端下行计数 | `retx=1381/23299` = **5.9%**（§3.5 修复 B 之前是 58%） |

但同时看到两件不可能的事：

- **客户端自报 `loss=73–77%`、`k` 顶到上限 6**，而下行还有 2 MB/s。真丢 73% 的链路撑不住这个速率。
  同一个客户端发给服务端的 FECSTAT，在服务端读出来是 `loss=0.0%`。
- **服务端残留一条半死会话**：`inflight=544166B queued=544172B retxSplit=51/1021/93`，
  1021 次 RTO 重传一直空转。

### 修复 D：FEC 本地兜底改成分片口径，不再按「1 秒组时钟」判失败

`AdaptiveFec.noteGroup(k, failed)` 的 `failed` 判据是「组在**首次收到符号后 1 秒**结算时
`orig+recov < n`」。这条路 srtt 560 ms、按 3.5 MB/s 算每秒有 ~360 个组在途——
1 秒结算时钟短于一整秒内组的飞行时间，于是 77% 的组在时钟到点时还没收全，
在一条分片丢失率 **0%** 的链路上被判成「失败」，把 k 一路抬到上限，
并把 `fecLoss`（stats 行打印的那个数）污染成 77%。

现在两边同源：**只数分片，不数「到点没齐的组」**。

- 首选仍是 FECSTAT：`1 - ΔdataRxOrig / (Δ(setsFull+setsPartial) × d)`；
- 对端不发 FECSTAT 时用本地兜底：同一个分子（`dataRxOrig`），但用**会话累计值**、
  按 FECSTAT 的 2 秒节奏采样。

**同时修掉一个静默 bug**：`k` 原来只在 `handleFecstat` 里同步给 `FrameTx`。
本地兜底把 k 改了却不进编码器——stats 行的 k 和线上真实奇偶校验可以整个会话都不一致。
新增 `Session.syncFecControl()` 每 tick 推送一次（`FrameTx.setK` 只写 `nextK`，在下个组开始时生效，
不会切组）。

**证据（同一时段，真实链路）**：修复前客户端 `k=6 loss=77.1%`；
修复后 `k=3→2→1`、`loss=0.0%`，服务端 `k=5→4` 随 FECSTAT 缓慢回落，
下行 2.33 MB/s、`retx=883/39500` = 2.2%、`retxSplit=859/24`（快重传/RTO = 36:1）。

### 修复 E：stateless reset 两端都要认；客户端断连要主动 RST

三条都在同一条链路上：

1. **只有 client 角色处理 stateless reset**，服务端收到直接忽略。
2. **客户端本地 socket 被掐断时不发 RST**，只是把会话从自己的表里删掉。
   此后对端的每个数据包都落进「未知 salt」，回一个 stateless reset——而服务端按 (1) 忽略它。
   被拒绝的包不刷新 `lastPeerInMs`，所以服务端唯一的退出是 135 秒后的 `peer_dead`，
   期间一直重传一个收不到的窗口。
3. **`makeReset()` 从来发不出去**：`NONCE_LIMIT` 是 2³²，而它取的是随机 **64 位**计数器，
   `sealAt()` 直接返回 null。之前所有 `stateless reset tx` 日志分支都是死代码。

改法：判定放在 bootstrap 探测**之前**（reset 本身就是合法的 bootstrap 信封，
放在后面会被 `hsEnv.open()` 当成结构错误吞掉）；两种角色都 `closed('stateless_reset')`；
客户端在 `sock.on('close')` 且流未正常结束时发 `STREAM_TYPE_RST`；
`makeReset()` 改从 nonce 空间顶部取值（`NONCE_LIMIT-1-random(16bit)`），
既在限内，也不会和从 0 起算的握手 nonce 撞车。

**证据（同一时段）**：服务端日志在中断后 **0.5 秒内**出现
`session ... closed: reset`（两次：一次 `curl --max-time` 掐断，一次正常结束），
不再有 544 KB 的僵尸会话；客户端 `loss` 读数恢复正常。

### 这一节里自己引入又修掉的两个坑

1. **本地兜底第一版用 10 ms 增量**：分片在 T 时刻到达、它所在的组在 T+1 s 结算，
   10 ms 窗口把「这一批到达」除以「上一批结算」，在读数为 0–4% 的链路上算出 **38.4%**。
   改成累计值 + 2 秒节奏后归零。教训与 §3.5 修复 C 相同：分子分母必须同窗口。
2. **reset 判定最初放在 `hsEnv.open()` 之后**：reset 用 bootstrap 密钥封装，
   `hsEnv.open()` 能解开它、发现里面不是 HELLO，于是记一次结构错误——服务端永远学不到对端已消失。
   必须按长度先认形状。

## 3.7 跨实现互通验证（2026-11-12，Node ↔ C++）

C++ 侧 `session.cc` 原来也在两处 reset 判定上加了 `role == kClient` 门槛（`on_wire` 的
`open_reset` 分支、`on_oob` 的 magic 分支），与 Node 侧修复前是同一个错误前提。已去掉，
并把 `session_test` 里那条**空断言**（reset 只投递给 client，server 从未收到，`!server.peer_dead()`
恒真）改成真实投递。C++ 门禁 Debug ctest **46/46**。

互通矩阵（环回，两端都指向同一个本机 345 MB 文件，避免外部网络抖动）：

| 组合 | 功能 | 修复前吞吐 | 修复后吞吐 |
|---|---|---|---|
| Node 客户端 → Node 服务端 | 200 | 13.1 MB/s | 10.28 MB/s |
| C++ 客户端 → C++ 服务端 | 200 | 3.9 MB/s | 2.95 MB/s |
| Node 客户端 → C++ 服务端 | 200；`curl` 掐断后 **0.2 s** 内 `conn 1 ... closed: reset` | **12.8 KB/s** | **3.41 MB/s** |
| C++ 客户端 → Node 服务端 | 200；中断后重建会话正常 | **71–89 KB/s** | **4.97 MB/s** |

「修复后」四组在同一窗口、同一目标文件、连续 8 s 采样跑完，跨实现已回到同实现量级。
「修复前」的两个混合数字虽来自更早时段，但**不是链路波动**：它们每次都确定性地在
**129018 字节**处永久卡死（与带宽无关），所以这个对比成立。

结论分两层：

1. **功能互通成立**，且中断收尾走的是带内 STREAM RST，不需要 stateless reset 兜底——
   `curl` 掐断后 0.2 s 内服务端就打出 `conn 1 ... closed: reset`。
2. **吞吐塌陷已定位并修复，根因不在 ACK/流控口径，而在信封层**（详见 3.7.1）。
   原先记下的 10 s 账 `queued=520180 acked=129018 retx=289 (rto=288)`、
   `cwnd=391162`、`bw=4433333`，约等于 1 个段 / 100 ms——那 289 次 RTO 重传
   全部解不开，不是"收尾干净"，也不是窗口算错。

### 3.7.1 根因：C++ 单方面执行 #84 epoch 滚动

**契约**：epoch key update 是握手 TLV type=4 承载的能力，必须**两端都提供**才启用。
Node 的实现是正确的：`this.env.setKeyUpdate(this.hs.tlvAgreed(TLV_TYPE_KEY_UPDATE))`，
且 `session.ts` 在该行上方的注释逐字预言了这个故障——「否则发送方会在
`FIRST_ROLL_AT` 包后开始滚密钥，而未选择启用的对端继续用会话密钥解密，链路悄无声息地死掉」。

C++ 的 `session.cc` 却写成 `set_key_update(cfg_.key_update && hs_.tlv_negotiated())`：
`tlv_negotiated()` 只说明**对端会说 TLV 扩展**，与是否支持 #84 无关。而 C++ 的本地
TLV 列表只有 `kTlvTypeAckV2`(2) 和 `kTlvTypePrewarm`(3)，**从不提供 type=4**。
于是任何混合会话都是：ack_v2 让 TLV 块协商成功 → C++ 在第 100 个数据报
（`kFirstRollAt`）换成 epoch-1 key，wire counter 从 `99` 跳到 `16777216`（`kEpochSpan`）；
Node 侧 `tlvAgreed(4)=false` 仍用 epoch-0 key，此后**每个**数据报 GCM 校验失败。

诊断链（每一步都可复现，不是推测）：

1. 客户端只收到 set 0–9 各 10 个 `type=0` 分片，之后 494 个包 `REJECT auth-fail`；
   `recvNext=129018` 与服务端 `acked=129018` 一致 → **不是 ACK 解析错位**，
   `reorder=0B` → 客户端也没积压乱序。
2. 关掉 FEC（`--fec=10:0`）后**仍在同一字节数 129018 处卡死** → 排除 parity 路径。
3. 在中间插一个 UDP 中继（`fcp/logs/udpmon.cjs`）读 wire 首部
   `salt(8) | counter(8 LE)`，抓到 S>C 序列 `...97, 98, 99, 16777216, 16777217, ...`
   → 锁定 epoch 滚动。注意 Node 的 `REJECT auth-fail` 日志把 tag 失败、重放拒收、
   counter 越界混为一谈，一度把排查方向带偏。

**修复在 C++ 侧，Node 零改动**：`handshake.h` 补 `kTlvTypeKeyUpdate = 4`；
`session.cc` 启用条件改为 `hs_.tlv_agreed(kTlvTypeKeyUpdate)`；`session.h` 加
`key_update_active()` 让这个决策可观测。C++ 仍不提供 type 4，因此修复后所有 C++
会话停在 epoch 0（单 key、counter 连续、2^32 上限），与 Node 一致。
两端的 epoch key 派生本身逐字节同构（`AES128(session_key, dir|'2'|epoch LE16|0^12)`），
所以缺的只是协商，不是算法；将来若要真正启用 #84，把 type 4 加进 C++ 本地 TLV 列表即可。

复验证据：修复后中继抓到数据平面 **20335 个包、`max_ctr=20810`、`epoch_jumps=0`**。
C++ 决策记录新增 **#92**，回归测试 `TestKeyUpdateNeedsBothEndsToAgree`
（含"强制开启时第 101 包必须跳到 kEpochSpan"的负向对照，防空断言），
Debug/Release ctest 各 46/46。

### 3.7.2 同窗口 A/B 固化（2026-11-12）

§3.7 的「修复前」两个数字来自更早时段，当时靠"每次都确定性地卡在 129018 B"论证它们不是链路波动。
这个论证成立，但仍不是严格的同窗口对照。本轮补上：**用真实旧行为二进制做对照组**。

对照组的构造（业务源码最终零改动）：

1. 备份 `src/fcp/session.cc`，记下 `git diff -- src/fcp/session.cc | sha256sum` 作为基准；
2. 临时把 `session.cc:642` 反改为 `hs_.tlv_negotiated()`，增量 Release 构建
   `fcp-server-old.exe` / `fcp-client-old.exe`（`build/artifacts/ab-old/`）；
3. **立即还原**源码：diff sha256 与基准一致（`665ca21a…`），且与备份 `cmp` 逐字节相同；
4. 再增量构建修复版 `fcp-server-fixed.exe` / `fcp-client-fixed.exe`
   （`build/artifacts/ab-fixed/`）。两组 exe 的 sha256 确实不同。

链路与顺序：本机环回，329 MiB 本地文件服务 → C++ server(UDP 4470) → Node client(SOCKS5 1080)
→ `curl` 采样 12 s；`build/ab-run.sh` 按 **F,O,O,F,F,O,O,F** 交替，让窗口内的任何漂移被两侧共享。

两点结论：

- 对照组四杆的方差几乎为零、字节数完全相同（128 840 B），这是**确定性协议故障**的指纹——
  第 100 包之后每个数据报 GCM 失败，只剩握手/重试的固定开销，与带宽、拥塞、时间窗无关。
  修复组的 ±8% 波动才是本机调度噪声。因此 §3.7 的 265×/60× 不是挑时段挑出来的。

  跨实现已落在同实现区间内，没有残留的独立瓶颈证据。

**局限（如实）**：本轮只做了 Node client → C++ server 方向；C++ client → Node server
方向的同窗口 A/B 未重跑（§3.7 里是跨时段数字）。两方向共用同一处 `set_key_update`
判定，因果相同，但**没有独立的同窗口证据**。产物（旧/新二进制、A/B 脚本、CSV、日志压缩包）
都在 `fcp/build/artifacts/`，由 `.gitignore` 排除，不入版本库。

六个核心源码文件本地与 VPS sha256 全一致；systemd `ExecStart` 为 `--fec=10:6`；

### 发现但未修：客户端遇到未知 salt 直接丢弃

`src/app/tunnel.ts` 的客户端 `onUdp` 只查 `sessions`，命中不到就 `return`——没有服务端那种
"born 分支建会话 → 验不过就回 stateless reset"。实测把客户端强杀后重启，旧 salt 的数据包
连续 96 个全部落在这个分支（`known=false`），客户端一个 reset 都没发，服务端只能等 135 s。
也就是说：**C++ 服务端新增的 reset 接收路径，在 Node 客户端作对端时不可达**。
修法需要新建一种"只用于回 reset 的裸会话"（现有 `createSession` 是服务端专用，带
`ServerTunnel`），并加一个每秒上限防会话 churn——属于独立改动，未在本轮落地。
注：上一轮曾为此临时加过 `--udp-port` 来固定 UDP 源端口以复现，按用户要求已删除，
现在该场景只能靠单元测试构造输入来验证。
