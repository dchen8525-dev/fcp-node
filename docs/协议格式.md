## 1. 协议栈分层

```
应用  ── SOCKS5 / HTTP CONNECT / absolute-form HTTP（本地 TCP，127.0.0.1:1080）
  │
  ├─ FCP OPEN / OPEN_OK / OPEN_ERR（隧道内前几个字节，不是独立帧）
  │
FCP-STREAM v1  ── 自研可靠字节流：DATA / ACK / ACK v2 / RST（字节偏移序号）
  │              （注意：不是 KCP，见 §10.0）
  │
FEC 集合层  ── 6 字节 FEC 头 + symbol，RS(n, k) 纠删，闭环自适应冗余
  │
加密信封  ── salt(8) | nonce(8) | AES-128-GCM 密文 | tag(12)
  │
UDP  ── 默认 :4460（服务端）/ 本地监听默认 :1080
```

**一条 UDP 报文 = 一个加密信封 = 一个 FEC 头 + 一个 symbol = 一个 FCP-STREAM 段。**
`docs/协议规格.md §4.3` 把它写成「一个 FEC symbol 恰好承载一个 KCP segment」，
代码里 `FrameTx::on_kcp_output()`（`src/fcp/frame_tx.cc:42`）的入参就是流层段，语义成立但名字过时。

## 2. 密钥材料与派生

### 2.1 PSK 与 salt

| 项 | 值 | 出处 |
|---|---|---|
| PSK | 16 字节，32 位十六进制。Node 侧只接受 `--key`（`--key-env` / `FCP_PSK` / `--key-file` / `--psk-file` / `-k` 均已删）；C++ 侧原本还有 `--key-file` 与环境变量回退 | `apps/cli/cli.cc:190-198` |
| salt | 8 字节，明文，每会话新画；服务端会话表按它查找 | `envelope.cc:118`、规格 §4.1 |

salt 既做会话查找键，也做会话密钥派生输入，**不是** nonce 起点。

### 2.2 四个派生函数（全部 AES-128 单块 ECB，Node `node:crypto` 可字节级复刻）

```
① X0 = AES128(PSK, salt(8) || 0x00×8)                       // derive_session_key
   → 握手信封（bootstrap）密钥，v7 起只承载 HELLO / HELLO_ACK，永不 rekey
                                                            envelope.cc:69-83

② X1 = AES128(PSK, X0 ⊕ client_nonce[16])
   X2 = AES128(PSK, X1 ⊕ server_nonce[16])                  // derive_session_key_v7
   → 数据面会话密钥；三块定长 CBC-MAC，无填充歧义
                                                            envelope.cc:118-144

③ SP 800-108 counter KDF（AES-128 PRF）：
   K(i) = AES128(session_key, [i]1 | label(6) | 0x00 | [L]8)
   label = "fcp-c2" / "fcp-s2"，L = 128 bits（8 字节大端），i 从 1 起
   key_c2s = K(1)@"fcp-c2"，key_s2c = K(1)@"fcp-s2"
                                                            envelope.cc:22-65, 85-92

④ epoch ≥ 1 的方向键（#84）：
   out = AES128(session_key, label(2) | epoch(2 LE) | 0x00×12)
   label = "c2" / "s2"                                      envelope.cc:94-113
```

**关键**：③ 的 16 字节输入块布局是 `counter | label6 | 0x00 | L_be8`，
`L` 是**输出位数的 8 字节大端表示**（16 字节 → 128 → `00...80`），不是长度字节。写错这里两端永远解不开。

### 2.3 双信封（R3-1）

| 信封 | 密钥 | 承载 | nonce 起点 | rekey |
|---|---|---|---|---|
| `hs_env` 握手信封 | ① X0 | 仅 `type=oob` 且 payload 为 HELLO / HELLO_ACK | **每会话 64 位 CSPRNG 抽样** | 永不 |
| `env` 数据信封 | ① X0 起，握手 `configure()` 后用 ② X2 `rekey()` | 全部数据 / parity / FECSTAT / keepalive / PMTUD | **0** | 一次 |

- 握手信封发送预算 `2^16` 包（`session.cc:50`），计数器高起点不消耗预算；
  `init_bootstrap_nonce()` 同时把接收上限开到整个 64 位空间（`envelope.cc:507-521`）。
- 握手信封接收侧**无 2^32 计数器上限**（对端自选落点）。
- 接收顺序：**先数据信封，失败再试握手信封**；握手信封解开后只放行 HELLO/HELLO_ACK，
  其余计 `struct_fail`（规格 §4.1 第 129-132 行）。稳态流量不付第二次 AES 代价。
- 重放过的 HELLO 会让新建会话重发 ACK，若握手计数器起点固定会造成 `(key, IV)` 重用，
  所以起点必须 CSPRNG；取不到熵源时 `Session::start()` 直接返回 `kNoEntropy`，**不允许退化**（`session.cc:187-191`）。

## 3. 第 1 层：加密信封

### 3.1 布局（`src/fcp/envelope.h:85-99`、规格 §4.1）

```
 0        8        16                                    N-12      N
 +--------+--------+-------------------------------------+---------+
 | salt 8 | nonce8 | AES-128-GCM 密文（= FEC头6 + symbol） | tag 12  |
 +--------+--------+-------------------------------------+---------+
  明文传输   LE u64   被加密 + 被认证                        96-bit
```

固定开销 **28 字节**（8 + 8 + 12）。AAD 为空。tag 12 字节（不是 16）。

### 3.2 IV 展开（`envelope.cc:14-20`）

```
IV[0..7]  = nonce_ctr (u64 LE)
IV[8]     = direction  (C2S = 0x01 / S2C = 0x02)   ← 不上线，由角色决定
IV[9..11] = 0x00 0x00 0x00
```

Node 侧：`createCipheriv('aes-128-gcm', key, iv, { authTagLength: 12 })`，
不调用 `setAAD`，`getAuthTag()` 即 12 字节线上 tag。

### 3.3 计数器与预算

| 常量 | 值 | 说明 |
|---|---|---|
| `kNonceLimit` | `2^32` | 单方向密钥的 GCM 调用上限（`envelope.h:94`） |
| `kEpochSpan` | `2^24` | 每个 epoch 的 nonce 跨度（`envelope.h:108`） |
| `kEpochSpaceEnd` | `65536 × 2^24` | key-update 模式的发送上限（`envelope.h:112`） |
| `kFirstRollAt` | 100 | 首次 roll 提前触发，让 rollover 路径在会话头几秒就被走到（`envelope.h:117`） |

`kReplayWindow = 1024`（`envelope.h:99`）—— **规格 §4.1 仍写 256，已过时，见 §12**。
窗口是 IPsec 式位图：`seen[delta]` 表示 `highest - delta` 已收过；
前跳超过窗口宽度时整表清零。`open()` 在 AES **之前**做纯判定 `nonce_window_may_accept()`，
tag 验证通过后才由 `accept_nonce()` 落状态，未认证包无法污染窗口（`envelope.cc:292-303, 322-347`）。

### 3.4 #84 epoch key update（仅 TLV 协商过的对端）

`nonce = epoch × 2^24 + counter`；epoch 从 nonce 高位读出，无需额外协商报文。
发送侧 roll 时重新派生该 epoch 的方向键并把 `send_nonce` 跳到新 epoch 基址；
接收侧最多同时保留 current + frozen previous 两个 epoch 的键与窗口
（`envelope.cc:239-263, 355-435`）。**epoch 0 的密钥与字节行为与旧 v7 完全一致**，
所以老对端不受影响。

**Node 侧：启用条件是双方都发布 TLV `type=4`**（`Session.keyUpdateActive`），且本端**总是**发布
它（`--key-update` 已删除，没有关闭方式），所以是否 roll 完全由对端能力决定。
C++ 侧原本只看「TLV 协商过」，那等于只看 CAP_TLV 位；ACK v2 常开后该位在
Node↔Node 之间恒为 1，于是只开一端就会在 `FIRST_ROLL_AT=100` 个包后开始用新键加密，
对端仍在用 session key，之后整条连接静默丢包（实测 500 KB 停在 318 701 B）。
按 `type=4` 协商后，对端不发布就自动降级为「不启用」，连接照常。

### 3.5 #86 stateless reset

服务端持有 PSK 但没有该 salt 的会话时，用**握手（bootstrap）信封**回一个 8 字节 magic：

```
明文 = 'F','C','P','R','S','T','1',0x00        // "FCPRST1\0"
报文总长 = 28 + 8 = 36， nonce 任意
```

`open_reset()` 绕过重放窗口（`envelope.cc:475-497`）。客户端收到后标记会话死亡并重连（`session.cc:725-738`）。

## 4. 第 2 层：FEC 头（6 字节，冻结）

`src/fcp/hdr.h:21-57`、`hdr.cc:1-56`

```
 offset size field    说明
 0      4    set_id   u32 LE，集合编号，u32 回绕用半窗比较
 4      1    index    0..S-1；data 为 0..n-1，parity 为 n+j
 5      1    type_k   (k << 5) | (j << 2) | type
```

| 字段 | 位 | 含义 |
|---|---|---|
| `type` | bit0-1 | 0=data，1=parity，2=oob，**3 未定义，收到计 struct_fail** |
| `j` | bit2-4 | 仅 parity 有效，本片在 parity 组内的序号 `0..k_eff-1` |
| `k` | bit5-7 | 本集合**计划**的 parity 数（集合开始时锁定，不是实际发出数） |

约束：
- `S = D + P ≤ 256`（index 是 u8）、`P ≤ 7`（k 占 3 位）、`j ≤ 7`。
  接收端按 `S = D + 本端协商 P` 校验，`index ≥ S` 直接判 `IndexPastS` 丢弃；
  因此**发送端的 k 也不能超过协商 P**，否则多出的 parity 只是白占带宽。
  Node 侧由 `AdaptiveFec.setParityCeiling(np.p)` 保证（`--fec-budget` 已删除）。
- `n`（本组实际 data 数）由任一 parity 直接给出：`n = index - j`，data 头里**没有** n。
- 稀疏流量按空闲超时提前闭合时 `n < D`，实际只发 `k_eff = max(1, ceil(k·n/D))` 条 parity，
  但 `k_eff` **不上线**，线上仍填计划的 `k`（`frame_tx.cc:96-140`）。
- 校验顺序（`hdr.cc:validate_hdr`）：oob 直接放行 → type 合法性 → `index < S`
  → data 的 `index < D` / `index < n`（若已知）→ parity 的 `j < k` 与 `1 ≤ index-j ≤ D`。
- `set_id` 比较用模 2^32 半窗：`seq_after(a,b) = (int32)(a-b) > 0`（`src/fcp/seq.h:20-30`）。

## 5. 第 3 层：symbol

### 5.1 data

```
symbol = len(2 LE) | payload
len 必须等于整个 symbol 的字节数（= 2 + payload_len）
```
构造见 `frame_tx.cc:56-70`，校验见 `frame_rx.cc:110-118`（`declared != symbol_len` → `struct_fail`）。

### 5.2 parity

```
symbol = RS 输出，长度恰好 symbol_max，无 len 字段
symbol_max = 本集合所有 data symbol 长度的最大值
```
发送前把每条 data symbol **零扩展到 symbol_max** 再算 parity；接收端靠任一 parity 的长度得到 `symbol_max`。
FEC 头**不在** RS 编码域内。

### 5.3 RS 编解码（`src/fcp/rs.cc`、`cauchy.cc`、`gf256.cc`）

- 域 `GF(2^8)`，约简多项式 `0x11D`，生成元 2（`gf256.h:21`）。
- Cauchy 系数 `coeff(r, c, k) = inv(uint8(r ^ (k + c)))`（`cauchy.cc:9-11`）。
- 编码：parity[r] = Σ_c coeff(r,c,k) · data[c]（`rs.cc:23-40`）。
- 解码：取前 `t` 条可用 parity 行，构造 `t×t` 系数矩阵，GF(2^8) 上高斯-约当求逆，
  RHS = parity ⊕ 已知 data 贡献，再乘逆矩阵还原缺失 data（`rs.cc:42-104`）。
- 边界：`n + k ≤ 256`，`k ≤ 7`，否则直接拒绝（避免 `(k+c)` 截断成 0 列）。

### 5.4 oob

```
hdr = { set_id = 0, index = 0, type_k = 0x02 }
symbol = 消息体（magic + 定长载荷）
```
oob 不占集合、不进 RS、不计丢包统计、不参与 symbol_max（`session.cc:1340-1352`）。

### 5.5 MTU 预算（`src/fcp/frame_tx.h:30-70`、规格 §4.6）

```
base        = M - H_ip - 8                  (IPv4 H_ip=20 / IPv6=40)
data wire   = 28 + 6 + 2 + payload        = 36 + payload
parity wire = 28 + 6 + symbol_max         = 34 + symbol_max
payload_max = base - 36
symbol_max  = base - 34 = payload_max + 2
mss         = payload_max - 24            (24 是 KCP 头保留量，见 §10.0)
合法条件    = base ≥ 36 + 24 + 1
```

| 场景 | payload_max | symbol_max | mss |
|---|---|---|---|
| IPv4, M=1400 | 1336 | 1338 | 1312 |
| IPv6, M=1400 | 1316 | 1318 | 1292 |

**启动期硬校验**：`mtu ≥ 6 + 128 + 28 + H_ip + 8`，否则最大的 FECSTAT oob 都发不出去，
`Session::start()` 返回 `kBadConfig`（`session.cc:40-43, 204-207`）。

## 6. 集合生命周期（行为契约，非字节布局）

**发送端**（`frame_tx.cc`）：集合开始时锁定 `k`；每来一个流层段立即成帧并发出 data；
`n == D` 闭合（Full）或距最后一个 symbol ≥ `flush_ms`（`clamp(srtt, 25, 200)`）闭合（Idle）；
闭合时算 `k_eff`、零扩展、RS 编码、发 `k_eff` 条 parity，`set_id++`。
`abort()` 只推进 `set_id`，不发 parity。

**接收端**（`frame_rx.cc` / `frame_rx_decode.cc`）：按 `set_id` 建集合状态；
data 的 `len` 自校验；parity 给出 `n`；收到 ≥ `n` 个 data 或可解线性方程组时交付；
已结算集合进墓碑（`retired_`），迟到分片不得二次结算（`frame_rx.cc:121-127`）。

**结算器**（`settle.h` / `settle.cc`）负责把集合账目转成 FECSTAT 计数；
**策略**（`strategy.h` / `strategy.cc`）按 `R(k)` 经验校正、三态控制器、字节预算（默认 0.80）
决定下一个 `k`，上限 `kDefaultPmax = 6`（`strategy.h:24`），硬上限 7。
这部分不改变线格式，只改变发多少 parity，细节见 `docs/M3控制设计.md`。

## 7. 握手层

### 7.1 消息布局（`handshake.h:75-85`、`handshake.cc:104-118`）

```
HELLO      = magic16 "FCP_HELLO_V1\0\0\0\0"
           | sender_nonce16 | caps4                         = 36 字节
HELLO_ACK  = magic16 "FCP_HELLO_ACK_V1"
           | client_nonce16 | server_nonce16 | caps4        = 52 字节

caps = ver(u8)=1 | data(u8) | parity(u8) | flags(u8)
```

magic 同时是握手版本号，整 16 字节精确比对，不匹配不识别不回应。
**注意**：规格 §6.1 末段写「oob 的 symbol = magic(16) | caps(4)」是旧描述，
与同页的 36/52 字节布局自相矛盾，按代码 36/52 实现。

### 7.2 caps 位（`handshake.h:50-66`）

| bit | 名称 | 性质 |
|---|---|---|
| 0 | `kCapFraming` | 必需 |
| 1 | `kCapFecstat` | 必需 |
| 2 | `kCapPerSetK` | 可选 |
| 3 | `kCapDeadline` | 可选 |
| 4 | `kCapPmtud` | 可选，仅在配置启用时置位（`session.cc:133-135`）；**不认识该位的对端会整包拒绝 caps，所以两端必须同版本** |
| 5 | `kCapTlv` | 可选，#77 |
| 6-7 | 保留，**必须为 0** | `kCapKnownMask = 0x3F` |

### 7.3 caps 校验与协商（`handshake.cc:52-59, 428-452`）

```
合法: ver==1, data>=1, parity<=7, (u16)data + (u16)parity <= 256, (flags & ~0x3F)==0
协商: flags   = local_flags & peer.flags
      required = FRAMING | FECSTAT，缺一 → kMissingCapability
      both_tlv = peer 带 kCapTlv 且本端确实发过 ext 形状
      D' = min(local_d, peer.data)
      P' = min(local_p, peer.parity)
      mode = (P' == 0) ? FramedStats : FramedRepair
```

### 7.4 TLV 块（#77，`handshake.h:86-110`）

紧跟在固定长度消息之后，仅当 `flags` 带 `kCapTlv`：

```
block_len(2 LE) | [ type(1) | len(1) | value(len) ] ...
```

- `block_len` 不含自身 2 字节；总消息长度必须 `== fixed + 2 + block_len`。
- `type=0` 非法；`len ≤ 255`；块总长 ≤ 1024。
- 未知 type 原样解析并忽略（前向兼容）。
- 已定义：`1` = ERROR（值 1 字节 = `HandshakeError`，让对端立刻失败而非跑完重试表）、
  `2` = ACK v2 能力、空值、`3` = prewarm 票据、12 字节、
  `4` = #84 key update 能力、空值（Node 侧新增，仅表示「我也能 roll」，roll 本身由 nonce 高位推导，无额外字段）。
- **降级探测**：客户端前两个 HELLO 带 TLV；若都无应答，第三个起改回无 TLV 的纯 v7 形状
  （`handshake.h:267-276`）。这是兼容「不认识 CAP_TLV 的对端」的降级路径；
  Node 版保留该能力，但按 §13.2 的验收线，当前不依赖任何 C++ 对端。

### 7.5 重传与状态机

- 时序：0 / 250 / 750 / 1750 / 3750 / 7750 / 15750 / 23750 / 31750 ms，
  共 9 次，约 39.7 s 判死（`handshake.h:112-126`，#76）。
  有 prewarm RTT 先验时首个间隔取 `clamp(2×srtt, 250, 8000)`。
- 重传由握手层自己的定时器承担，**不经流层、不经 KCP**。
- 两端可同时发 HELLO；每个合法 HELLO 都回 ACK；角色由 `Direction` 固定
  （C2S 端贡献 client_nonce），不靠谁先开口，因此同时打开收敛到同一把密钥。
- ACK 的 echo 校验：客户端比 `client_nonce`、服务端比 `server_nonce` 与本地 draw 逐字节相等，
  不等丢弃并计 `nonce_mismatch_`。
- 已建立会话收到 HELLO：nonce 相同 → 幂等重发 ACK；nonce 不同 → 拒绝、状态不动（R3-24）。
- 协商完成前 data 全部进缓存，上限 512 段 / 512 KiB；溢出 → `kCacheOverflow` 断连。

### 8.2 PMTUD（`pmtu.h:70-95`）

```
magic8 "FCP_PMTU" | type1 (0=probe,1=ack) | reserved1 | token4 LE | mtu2 LE
= 16 字节头，probe 后面补 0 到 pmtu_probe_len()，使整包恰好等于待测 MTU
pmtu_probe_len(M) = (M - H_ip - 8) - 28 - 6
```
探测间隔 5×SRTT，连续 3 个丢失探测判黑洞，搜索收敛差 ≤ 20 字节，接收硬上限 `kPmtuAbsoluteMaxMtu = 9000`。

### 8.3 prewarm 票据（#87，`prewarm.h:76-90`）

TLV type 3 的 value，定长 12 字节，全 LE：

```
ver(1)=1 | initial_k(1) | srtt_ms(2) | window_kb(3) | bw_kbps(3) | min_rtt_ms(2)
```
`initial_k = 0x0F` 表示无测量值；8..14 保留且解码时拒绝。
它只是**先验**，接收端还要按本地配置钳位（`window_max_bytes` 上限），持有 PSK 的对端无法用它把控制器推到本机不可能产生的状态。

## 10. FCP-STREAM v1（可靠字节流）

### 10.0 先澄清：这里没有 KCP

`README.md:4` 写「基于 KCP」，`docs/协议规格.md §9` 整节按 KCP 假设描述，
但**当前源码里不存在任何 KCP 实现**：全库仅剩 `kKcpHeaderReserve = 24`（MTU 保留量）、
`kcp_sn_of()`（从 payload+12 读 u32 的遗留去重键）和若干函数名。
`src/fcp/stream.h:1-10` 明确写着：ARQ 由本文件承担，即「KCP 本来要占的那个位置」。
`session.h:100-104` 进一步规定 **FCP-STREAM 必须把 `sn_of` 置空**，
因为它按字节编号，重传故意重复同一 id，在这一层去重会让发送窗口永久停摆。

**移植结论**：Node 版只实现 FCP-STREAM，不移植 KCP；
`mss = payload_max - 24` 里的 24 作为常量保留即可，不要去找 KCP 头。

### 10.1 段类型（`stream.h:35-60`，全部 LE）

| type | 名称 | 布局 |
|---:|---|---|
| 1 | DATA | `type(1) \| seq(4 LE) \| flags(1) \| payload` — 头 6 字节；`flags bit0 = FIN` |
| 2 | ACK | `type \| cum(4) \| rwnd(4) \| sack_start(4) \| sack_end(4)` — 17 字节 |
| 4 | ACK v2 | `type \| cum(4) \| rwnd(4) \| n_ranges(1)` + `(gap, len)` varint 对 — 头 10 字节，最多 64 组 |
| 3 | RST | `type \| code` — 2 字节，`code=1` = abort |

构造代码：`stream.cc:478-484`（DATA）、`stream_recv.cc:291-317`（ACK）、
`stream_recv.cc:329-353`（ACK v2，`buf[9]` 在最后回填 `n_ranges`）、`stream.cc:136`（RST）。

- **序号是字节偏移，不是包号**；`cum` = 已连续交付的字节数，FIN 占最后一个字节偏移 +1。
- DATA 的 `seq` 用 `put_le32(seg.offset)`；所有 u32 比较走 §4 的模半窗规则。
- ACK 的 SACK 是**单块**；重复 cum 时接收端轮转 `oob_` 里的块，让每个洞在几次 dup-ACK 内被报出。
- ACK v2 的 `(gap, len)` 是相对 `cum` / 上一块末尾的 LEB128 uvarint（`wire.h:84-110`），
  编码本身跨 u32 回绕安全；必须整组校验通过后才应用（`stream_send.cc:76-115`）。
- ACK v2 **只在双方 TLV 都提供 type 2 时启用**，老对端永远只能收到 17 字节 v1 ACK。
- 未知 type 忽略并计 `bad_segs_`，不杀会话（`stream.cc:169-173`）。

### 10.2 与 FEC 的关系

FEC 只修复 RS 能修的擦除，**不重传**；ARQ 由 FCP-STREAM 负责。
一个流层段 = 一个 data symbol = 一个 UDP 报文，段边界在线上保留，
因此 FCP-STREAM 不需要长度前缀。

## 11. 代理入口（本地 TCP → 隧道）

`src/proxy/proxy_proto.h` 全部是纯函数解析器，多字节字段为**网络序 BE**。
一个本地连接 = 一个 FCP 会话 = 一个目标；
HTTP absolute-form 正向代理是**每条请求一条会话**，请求头强制 `Connection: close`，靠源站 FIN 收尾。

### 11.1 SOCKS5（RFC 1928，仅 CONNECT）

```
greeting : ver(1)=5 | nmethods(1) | methods[n]
reply    : ver=5 | method=0x00（无认证）/ 0xFF（无可用方法）
request  : ver=5 | cmd=1 | rsv=0 | atyp | addr | port(2 BE)
response : ver=5 | rep | rsv=0 | atyp=1 | 0.0.0.0 | port(2)=0      // 10 字节
```
`atyp`：`1`=IPv4(4B)、`3`=域名(1 字节长度 + 内容)、`4`=IPv6(16B)。
`nmethods=0`、RSV≠0、域名长度 0、port=0 一律 `kMalformed` 且不回复直接关闭。
上限：greeting 257 B、request 262 B。

### 11.2 HTTP CONNECT

```
CONNECT host:port HTTP/1.x\r\n ... \r\n\r\n
成功回 "HTTP/1.1 200 Connection Established"
```
目标一律 `atyp=3`（域名），包括 IP 字面量（解析在远端做）；IPv6 字面量的方括号去掉。
请求头总预算 8192 B，host 最长 255 B。非 CONNECT 方法先报 `kMethodNotAllowed`，
宿主再尝试 absolute-form 解析。

### 11.3 HTTP absolute-form 正向代理

`GET http://host[:port]/path HTTP/1.1` → 重写成 origin-form 请求头（强制 `Connection: close`），
目标仍走 FCP OPEN；`https://` absolute-form 是 `kBadRequest`（TLS 必须走 CONNECT）。
默认端口 80。请求体不碰，头部之后的字节原样转发。

### 11.4 FCP OPEN（隧道流的前几个字节，**不是独立帧**）

```
OPEN     = "FCPO"(4) | ver(1)=1 | atyp(1) | len(1) | addr(len) | port(2 BE)
OPEN_OK  = "FCPO"(4) | ver(1)=1 | kind=0x01 | reserved(2)=0        // 8 字节
OPEN_ERR = "FCPO"(4) | ver(1)=1 | kind=0xFF | code(1)              // 7 字节
```
- `atyp` 与 SOCKS5 共用同一组线上值；`len` 对数值型 atyp 必须等于 4 / 16，域名型 1..255。
- 最长 OPEN = 9 + 255 = 264 字节；`len=0` 或 `port=0` 为 `kBadAddress`。
- `OpenError`：`1` refused、`2` DNS、`3` target timeout、`4` not supported、`5` too many sessions。
- `OPEN_OK` 的保留字节必须为 0（`kBadReserved`）。
- 回复不对称（8 vs 7 字节）是规格 §4.3 的既定形状，不要"修正"成对齐。

### 11.5 三种入口的自动分流

同一个 `127.0.0.1:1080` 端口按**首字节 / 方法**分流：
`0x05` → SOCKS5；`CONNECT ` → HTTP CONNECT；其它 HTTP 方法 → absolute-form 正向代理。
