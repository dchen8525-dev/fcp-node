### 2.2 异常：历史会话持续广播 FECSTAT

客户端 864 个 `known=false` 包中，绝大多数是 **162 B**：

```
[07:29:08.361Z] DEBUG [97712414] udp rx 162B known=false
[07:29:50.171Z] DEBUG [1ef6097b] udp rx 1012B known=false
```

`162 = 28 (GCM 信封) + 6 (FEC 头) + 128 (FECSTAT)`。服务端日志给出原因：

```
[07:29:18.255Z] DEBUG [84aeee2d] CLOSE peer_dead (silent 135004ms)
[07:29:18.738Z] WARN  session b4cc437d7c2a4af3 closed: peer_dead
... 共 22 条
```

即：先前测试遗留的会话要静默 **135 s**（`PEER_ALIVE_GRACE_MS`）才被判死，期间仍周期性发 FECSTAT
与重传，且这些包被送到了同一个客户端地址。客户端早已删除对应会话表项，只能丢弃。
服务端 `udp_tx 9,926` 接近 `udp_rx 5,631` 的两倍、`oob_tx 1,985`，正是这种单向广播。

**影响**：不影响新会话功能，但放大 UDP 流量、撑大日志与内存。
当前服务 `active`、`NRestarts=0`、内存 89 MB、日志 16 MB、磁盘 51%。

## 3. 根因（按严重度分层）

### 致命：服务端丢弃 `Session.write()` 的未接收字节

`src/stream/stream.ts:107-116` 的 `write()` 只把前 `take` 字节放进 `pending` 并返回 `take`，
**余数字节必须由调用方保存重发**。客户端路径有 `flushPending()` 队列做这件事（`tunnel.ts:179-185`），
但服务端 `target -> tunnel` 路径没有：

```ts
// src/app/tunnel.ts:528-538
sock.on('data', (chunk: Buffer) => {
  const n = t.session.write(chunk);
  this.dbg(`... target->tunnel ${n}/${chunk.length}B`);
  if (n < chunk.length) {
    sock.pause();                       // 只挡住新数据，不补发余数
    const resume = setInterval(() => {
      if (t.session.streamRef.canWrite || sock.destroyed) { clearInterval(resume); sock.resume(); }
    }, TICK_MS);                        // 恢复后余数已被永久丢弃
  }
});
sock.on('end', () => t.session.closeWrite());   // 还有未发数据时就发 FIN
```

**决定性证据链**：

1. VPS 本地生成 512 KiB 确定性内容文件（sha256 `0f89e407…a158`，524,288 B），
   经隧道下载并逐字节比对：

   | 入口 | curl rc | 实收 | 缺失 | sha256 | 错误 |
   |---|---|---|---|---|---|
   | socks5 | 18 | 524,078 B | **210 B** | 不匹配 | `end of response with 210 bytes missing` |
   | http-forward | 18 | 524,070 B | **218 B** | 不匹配 | `end of response with 218 bytes missing` |

2. 服务端日志精确抓到同一次丢弃，与 218 B 缺失**完全一致**：

   ```
   [07:42:21.275Z] DEBUG [a078455d] target->tunnel 48422/48640B   → lost = 218 B
   ```

3. 尾部 TLS 记录 / `close_notify` 被截断，Windows Schannel 因此报
   `server closed abruptly (missing close_notify)` 或 `SEC_E_DECRYPT_FAILURE`；
   有 Content-Length 的下载读完即止，绕开了这个缺口。

### 重要：历史会话 135 s 才回收

`session.ts:443` 的 `PEER_ALIVE_GRACE_MS = 135000`。本地连接关闭时未主动通知对端拆会话，
造成 §2.2 的 FECSTAT 广播风暴。批量压测后这种现象会随历史会话数持续累积。

### 建议：运维与性能

- `--log-level=debug` 逐包记录，42 s 产生 7.7 万行 / 约 25 MB；无轮转，长时间手动测试会撑满磁盘。
  建议手动测完降为 `--log-level=info`，或加 logrotate。
- `--mtu-min=1040 + --parity=3`（30% 固定冗余）下聚合吞吐约 39 KB/s，大页面偏慢。调参需两端同时改并复测，
  本轮未擅自改动。
- 客户端 `sendOpen()` 里 `session.write(open)` / `session.write(firstPayload)` 未检查返回值，
  存在同类潜在丢字节风险（本次未触发，因为 OPEN 包很小）。

## 4. 建议的修复方案（**未实施，待确认**）

1. **服务端补发队列**：`ServerTunnel` 增加 `pendingToTunnel: Buffer[]`；
   `n < chunk.length` 时把 `chunk.subarray(n)` 入队并 `sock.pause()`；
   在 `TunnelServer.tick()` 中先 flush 队列、队列空且 `streamRef.canWrite` 后再 `sock.resume()`。
2. **延迟 FIN**：`sock.on('end')` 改为「排队尾字节 → 等 `pendingToTunnel` 清空、
   stream `pending` 排空且全部 ACK」后再 `closeWrite()`；设置兜底超时避免悬挂。
3. **客户端对称加固**：`sendOpen()` 对 `write()` 返回值走 `flushPending()` 同一队列。
4. **会话回收**：本地连接关闭时主动发 RST/reset；或把 `PEER_ALIVE_GRACE_MS` 降到可配置值，
   并在 `cb.closed()` 里立即删除会话表项。
5. **回归门禁**：512 KiB sha256 对拍（两种入口）→ github / cloudflare 首页 → 25 站点批量 →
   `node scripts/check.mjs`（18 模块 / 34 测试 / self-interop 7/7）。
