# 四代理吞吐对比：FCP vs kcptun vs 裸 TCP vs 裸 UDP

2026-11-12，同一台本机 → 同一台 VPS（`144.34.186.164`）→ 同一目标文件。
四个实现都提供 SOCKS5 入口，curl 只改 `-x socks5h://127.0.0.1:<port>`，其余参数一致。

## 0. 结论

1. **排序稳定：kcptun > FCP > 自写 TCP 隧道 > 自写裸 UDP（不可用）**。
   两个互相独立的指标（4 MiB 完赛时间、45 s 窗口采样）给出同一个顺序，各 3～6 个样本。
2. **kcptun 比 FCP 快 2.8 倍**（中位 390 vs 141 KB/s）。FCP 的 FEC 比例（10:3）与
   kcptun 默认相同，差在 ARQ/窗口/重传策略上，不是编码开销。
3. **TCP-over-TCP 最差，比 kcptun 慢 4.5 倍**（87 KB/s），但延迟最低（0.83 s）。
   两层各做一遍重传，在丢包路径上放大成 RTO 停顿，这个结果是结构性的。
4. **裸 UDP 不是代理**：它连完整的 TLS 流都送不完（4 MiB 请求只到达 8 806 B 就断）。
   它唯一有意义的数字是**链路容量上限**：1.05 MB/s。KCP 用到 37%，FCP 13%，TCP 8%。
5. 以上全部在**链路严重拥塞的时段**测得。同一 FCP 配置在 07:39 还有 2.38 MB/s，
   09:00 只剩 0.14 MB/s，而 VPS 直连源站始终 95 MB/s。**绝对数字只代表那个时段，
   排序和完整性结论才是可迁移的。**

## 1. 被测对象

| 代理 | 入口 | 实现 | VPS 侧 | 关键参数 |
|---|---|---|---|---|
| FCP | `127.0.0.1:1080` | `fcp-node` 现有实现 | UDP 4461 | `--fec=10:3`，PMTUD 1040→1500，窗口 512 KiB |
| kcptun | `127.0.0.1:1083` | `xtaci/kcptun` 官方源码编译 | UDP 7003 → 本地 1090 | 全默认：`--mode=fast`、`--mtu=1350`、`--ds=10 --ps=3`、`--sndwnd=128 --rcvwnd=512` |
| 自写 TCP 隧道 | `127.0.0.1:1081` | `bench/tcp-proxy.ts`（本仓库） | TCP 7001 | 每连接一条 TCP，`TCP_NODELAY`，无加密无复用 |
| 自写裸 UDP | `127.0.0.1:1082` | `bench/udp-proxy.ts`（本仓库） | UDP 7002 | 1400 B 载荷、32 位序号、按序交付；**数据帧不重传、无拥塞控制**；收发缓冲 32 MiB |

三处必要的公平性说明：

- kcptun 不是 SOCKS 代理，只做端口转发，所以 VPS 侧挂了一个 60 行的
  `bench/socks-server.ts`（127.0.0.1:1090）当它的下游。FCP 和自写两个代理是自己
  终结 SOCKS 的，这一跳只多一次 loopback，量级上可忽略。
- 自写两个代理由我按同一套代码风格写，缓冲 32 MiB；kcptun 用**操作系统默认 socket
  缓冲**（Windows 默认小得多），FCP 是 4 MiB。**kcptun 是在吃亏的条件下赢的。**
- kcptun 用 `--mode=fast` 出厂预设，我没有替它调参。另外单独试过 `--mode=fast3`，
  两次 41.9 s / 15.0 s，比 fast 更慢更飘（样本只有 2，不足以下结论）。

kcptun 构建来源：`go install github.com/xtaci/kcptun/{server,client}@latest`，
解析到 `v0.0.0-20261111062728-95dc3199ce44`（该仓库没有可用的 Release 资产，
`@latest` 落到 master 伪版本），工具链 go1.26.11，在 VPS 上交叉编译出 Windows 客户端。

## 2. 测试时段与链路状态

| 时间（北京） | 测量 | 结果 |
|---|---|---|
| 07:30–07:39 | FCP 完整下载 329 MB | **2.38 MB/s**（144.77 s，sha256 已验） |
| 09:00 前后 | FCP 20 s 采样 | 0.14 / 0.44 / 0.37 MB/s |
| 09:05 | VPS 直连源站 | **94.9 MB/s** |
| 09:10 | 裸 UDP 容量（32 MiB 猛发） | **1.05 MB/s**，丢 1.7% |
| 09:35 | 裸 UDP 容量（同上，16 MiB） | **0.53 MB/s** |

VPS 出口 95 MB/s、链路容量从 43 MB/s（前一日）掉到 0.5–1 MB/s，说明瓶颈在跨境
这一段，且在这个时段剧烈波动。**所以下面所有绝对值都是"坏时段"的数字。**

采样设计上做了两件事避免自欺：

- **交错采样 + 轮转顺序**：每轮把三个代理各测一次，且起始顺序按轮次旋转，
  让拥塞突发摊到所有人身上，而不是全落在"刚好排在最后"的那个身上。
- **短窗口只作辅助**：15 s 采样前后两批得出的排序直接反转（KCP 57→127 KB/s、
  FCP 252→66 KB/s），说明 15 s 与链路波动同量级，不足以区分三者。真正的主指标是
  **4 MiB 完整传输的完赛时间**，它对整段波动做积分。

## 3. 主指标：4 MiB 完整传输（前 4 MiB，Range 请求，各 3 次）

参考哈希：`d297e117c17102480e279bf4f09facee0f8f2282f3904f8169ed2d0f915ecb2c`
（4 194 304 B，在 VPS 上直取同 Range 计算）

| 代理 | 完赛时间 | 中位时间 | 中位速率 | 相对 FCP | sha256 |
|---|---|---|---|---|---|
| kcptun（fast） | 11.35 / 10.75 / 8.83 s | **10.75 s** | **390 KB/s** | 2.8× | ✅ 精确匹配 |
| FCP | 29.73 / 35.64 / 25.67 s | **29.73 s** | **141 KB/s** | 1.0× | ✅ 精确匹配 |
| 自写 TCP | 47.95 / 49.57 / 45.44 s | **47.95 s** | **87 KB/s** | 0.62× | ✅ 精确匹配 |
| 自写裸 UDP | 1.87 s 后 8 806 B 即断 | — | — | — | ❌ 截断 |

三个可靠代理的三次测量都很集中（KCP 8.8–11.3 s、FCP 25.7–35.6 s、TCP 45.4–49.6 s），
排序在每一次重复里都成立，不是靠取中位凑出来的。

## 4. 辅助指标

### 45 s 窗口采样（每代理 6 个样本，轮转顺序，中位）

| 代理 | 样本（B/s） | 中位 |
|---|---|---|
| kcptun | 227 706 / 386 541 / 490 059 / 225 172 / 210 395 / 458 257 | **307 KB/s** |
| FCP | 205 769 / 144 378 / 163 577 / 52 024 / 129 152 / 119 259 | **137 KB/s** |
| 自写 TCP | 56 800 / 60 424 / 32 393 / 93 683 / 100 303 / 60 085 | **60 KB/s** |

与主指标同序（KCP 2.2× FCP，FCP 2.3× TCP）。这一组整体低于 4 MiB 完赛速率，
因为窗口里还包含每次新建连接时的握手与慢启动。

### 小请求延迟（`https://example.com`，含 TLS，各 3 次，中位）

| 代理 | 延迟 | 说明 |
|---|---|---|
| 自写 TCP | **0.83 s** | 最快，没有 FEC 编解码和额外 framing |
| FCP | **1.11 s** | |
| kcptun | **1.29 s** | 最慢，KCP 的重传定时器与 FEC 组等待叠加 |

延迟排序和吞吐排序正好相反。这不是矛盾：吞吐靠"多发送 + 丢包后补"，延迟靠
"少等待"。KCP 为吞吐付出的排队代价体现在这里。

### 裸 UDP 链路容量

| 请求量 | 到达 | 耗时 | 速率 | 丢包 |
|---|---|---|---|---|
| 32 MiB | 32 994 432 B | 30.0 s | 1.05 MB/s | 1.7% |
| 16 MiB | 16 759 016 B | 30.0 s | 0.53 MB/s | 0.1% |

这是"不重传、不拥塞控制、只管猛发"时链路能给的全部。三个可用代理相对这个上限的
利用率：**kcptun 37%、FCP 13%、TCP 8%**。

## 5. 为什么裸 UDP 不能算代理

4 MiB 请求的真实表现：SOCKS 握手成功、HTTP 响应头（206）拿到了、**正文只到
8 806 B 就断**。

原因是结构性的，不是参数问题：

1. TLS 要求字节流严格按序。UDP 丢了就是丢了，只能等 `GAP_SKIP_MS=250` 后**跳过缺口**，
   一跳过，后面的密文全部错位，MAC 校验失败，连接直接死。
2. 想不跳缺口就得重传——那就是在实现 ARQ，也就不是"裸 UDP"了。
3. 所以裸 UDP 只能测量容量，不能承载任何真实流量。它的价值是**给出分母**。

想让它能用，就必须加回三样东西：序号确认、重传、拥塞控制。加完这三样，你得到的就是
KCP 或 FCP。

## 6. 结果怎么解释

**TCP-over-TCP 为什么最差（87 KB/s）。** 内层 TCP（curl↔本地代理）和外层 TCP
（本地↔VPS）各自维护重传。外层的丢包被内层当成拥塞，内层退让、外层 RTO 又拉长，
两个控制环路互相干扰；一次 200 ms RTT 的丢包，可能让内层停顿数秒。这是
"隧道里不要跑 TCP"的经典结论，本次数据完全吻合。

**FCP 为什么比 kcptun 慢 2.8 倍。** 两者 FEC 都是 10:3，MTU 同量级，差别在：
FCP 文档自己记着重传率约 58%、`updateStreamWindows` 用接收向估计推发送窗口（方向可疑）、
FEC 控制器停在灰区不升不降。在这个丢包路径上，这些正是决定性的。**结论是：我这套
FCP 的调参没有超过一个成熟 KCP 实现，不要把它当成"已经调优"的证据。**

**kcptun 为什么快。** 成熟的 ARQ（KCP 的 RTO 计算与快速重传）、更大的窗口
（rcvwnd 512 包 ≈ 691 KB）、以及 kcptun 自己那套 smux 复用。它在 Windows 上还是
默认小缓冲，说明它的优势来自算法而不是运气。

## 7. 局限

1. **只有一条链路、一个时段**，而且这个时段链路在崩。绝对值不可外推。
2. 每组只有 3（主指标）到 6（窗口）个样本。对"KCP > FCP > TCP"这个排序够用，
   对"2.8 倍"这种精确倍数不够用。
3. **没有测上行**。全部是下载方向。
4. **没有测长时间稳定性**。每次传输 4 MiB，最长的单次 50 s。
5. 自写两个代理是 200 行级别的教学实现，没有做连接复用、拥塞控制、公平性，
   它们代表的是"最朴素实现"的下限，不是 TCP/UDP 隧道这类方案的上限。
6. `fast3` 对照组只有 2 个样本，只记现象不下结论。

## 8. 复现

```sh
# VPS（代码在 /opt/bench，二进制在 /opt/bench/bin）
sh /opt/bench/start.sh          # socks-server:1090, tcp:7001, udp:7002, kcptun:7003
# 本机
sh bench/start-local.sh         # fcp:1080, tcp:1081, udp:1082, kcptun:1083
sh bench/matrix.sh 45 3         # 交错采样（秒, 轮数）
node bench/udp-proxy.ts sink --peer=<vps>:7002 --bytes=33554432   # 链路容量
```

对照进程全部停掉后，VPS 上只剩原有的 `fcp-node.service`（UDP 4461）在跑。
